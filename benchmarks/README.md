# AIRadar detection benchmark (first slice)

A reproducible, CPU-only, torch-free benchmark for the **classical CFAR detectors that
already ship in this repository**. It exists because the repo contains a large amount of
radar simulation, detection and model code but has never published a single measured
detection number, and the one script that attempted a comparison
(`AIRadar/AIradar_model_comparison.py`) cannot be imported at all: it does
`from AIradar_transformer import RadarTransformerNet` and
`from AImodels_joint import RadarNet, RadarTimeToFreqNet`, and neither module exists anywhere
in the repository (those classes live in `AIRadarLib/modeling_transformer.py` and
`AIRadarLib/modeling_RadarNet.py`). That failure is independent of torch.

Everything below is generated by one command. The results table in this file is written
by the benchmark itself, not typed by hand.

```
python -m benchmarks.run_benchmark --update-readme
```

## What is measured

Three detectors, all repo code, called unmodified:

| name | source | what it is |
|---|---|---|
| `cfar_numpy_go` | `AIRadar/AIRadarLib/radar_det.py::cfar_2d_numpy` | GO-CFAR on the **dB-magnitude** map. The threshold offset is hard-coded at +12 dB; the function has no `Pfa` argument. |
| `cfar_advanced_go` | `AIRadar/AIRadarLib/radar_det.py::cfar_2d_advanced` | GO-CFAR on **linear power** with the threshold multiplier derived from a requested `Pfa`, plus connected-component pruning and the shipped `min_snr_db=6` post-filter. |
| `cfar_custom_datasetv8` | `AIRadar/AIradar_datasetv8.py::AIRadarDataset._cfar_2d_custom` | The detector the dataset pipeline actually calls. GO-CFAR on the dB map with the config's `threshold_offset` (15 dB for the configs used here). |

Scenes come from the repo's own FMCW model, also called unmodified:
`AIRadarDataset.generate_targets`, `_generate_clutter_targets`, `_generate_coupling_target`,
`simulate_fmcw_signal` and `create_target_mask`.

Reported per (detector, scenario, SNR point):

* **Pd** — probability of detection: total true positives / total ground-truth targets.
* **FA/frame** — total false positives / number of frames.
* **FA rate /cell** — total false positives / (frames x eligible cells). "Eligible" mirrors
  each detector's own gating (`range_gate_low < range < R_max`, `|velocity| < v_max`), so the
  denominator is honest. This counts **post-NMS peaks**, not raw threshold crossings, and is
  therefore *not* comparable to a CFAR design `Pfa`.
* **range RMSE / velocity RMSE** — over matched pairs only, against each target's
  *continuous* truth (not its bin centre). Undefined (`n/a`) when nothing matched.
* **peak SNR** — measured mean target-peak-minus-noise-floor in the range-Doppler map, where
  the noise floor is the median dB level of cells at least 6 bins away from every target.
  See "the SNR axis" below for why this column matters.

## The association rule

A detection is matched to a ground-truth target iff **both** hold:

* `|detection.range_bin - target.range_bin| <= gate_range_bins` (default **2** range bins)
* `|detection.doppler_bin - target.doppler_bin| <= gate_doppler_bins` (default **1** Doppler bin)

where the target's bins are its nearest-bin quantization onto `range_axis` / `velocity_axis` —
the same rule `AIRadarDataset.create_target_mask` uses, verified by a unit test.

Matching is **one-to-one and greedy**: every candidate pair inside the gate is scored by the
normalized gate distance `sqrt((dr/Gr)^2 + (dd/Gd)^2)`, pairs are sorted by
`(distance, target_index, detection_index)`, and accepted while both endpoints are still free.
A target can claim at most one detection; every other detection in its gate counts as a false
positive. Unmatched targets are false negatives.

Why bins and not metres: with `zero_pad_factor=2` the range FFT grid is oversampled, so the
range **bin spacing** is `c/(4B)` while the true (Rayleigh) range **resolution** is `c/(2B)`.
The default gate of +/-2 range bins is therefore exactly one true resolution cell. Gating in
bins keeps that relationship explicit and avoids the dimensionally inconsistent
`sqrt(metres^2 + (metres/second)^2)` distance used by
`AIRadarDataset._evaluate_metrics` (see "Repo issues found" below).

Both gates are CLI flags (`--gate-range-bins`, `--gate-doppler-bins`) and their values are
recorded in `results/results.json`, so a different choice is reproducible rather than hidden.

## The SNR axis (read this before interpreting Pd)

The `snr_db` argument of `simulate_fmcw_signal` is a **time-domain** SNR: the noise variance is
set relative to the mean power of the *windowed beat signal*, before any FFT. Coherent range +
Doppler integration over `Ns x Nc` samples then adds tens of dB before the detector sees the
map. For `config_phaser` (1000 samples x 64 chirps) the coherent gain is
`10*log10(1000*64) = 48 dB` less about 1.76 dB of Hann window loss per axis, i.e. **~45 dB**,
which is what the measured `peak SNR` column shows. An input SNR of -20 dB therefore
corresponds to a ~25 dB peak in the range-Doppler map, where every detector saturates at
Pd = 1.

That is why the sweep runs from -50 dB to -15 dB rather than over "sensible" positive SNRs, and
why the measured `peak SNR` column is reported alongside: it is the number that actually
predicts detection. A sweep over positive input SNR would produce Pd = 1.000 everywhere and
say nothing.

## The scenario axis

| scenario | settings | meaning |
|---|---|---|
| `clutter_off` | `apply_realistic_effects=False` | single point target plus AWGN |
| `clutter_default` | `apply_realistic_effects=True`, `clutter_intensity=1.0` | exactly what the repo's dataset pipeline ships |
| `clutter_strong` | `apply_realistic_effects=True`, `clutter_intensity=1e4` | clutter RCS raised by +40 dB |

`clutter_strong` exists because of a measurement, not a hunch: at the shipped
`clutter_intensity=1.0`, `_generate_clutter_targets` draws RCS in -50..-20 dBsm while
`generate_targets` draws primary-target RCS in +5..+30 dBsm. The measured
clutter-to-target RCS power ratio is **-24.5 dB**, and enabling clutter perturbs the
range-Doppler map by only ~0.03 dB on average.

The consequence, measured: across the full 24-row `clutter_off` and `clutter_default` tables
below, **every Pd, TP, FN, range RMSE and velocity RMSE value is identical**. The only
differences anywhere are the mean peak SNR (by 0.001-0.017 dB) and a single false-positive
count (`cfar_numpy_go` at -20 dB: 78 vs 79 out of ~5 per frame). The shipped
`apply_realistic_effects=True` is effectively a no-op for detection metrics. Scaling the
clutter RCS by +40 dB (`clutter_strong`, measured **+15.5 dB** clutter-to-target) is what
finally moves the curves. The exact measured ratio for each scenario is in the generated table
and in `results/results.json`.

### Reading the results

Six things the numbers above actually say. All of them are re-derivable from
`results/summary.csv`.

1. **The transition is real, not saturated.** Every detector moves from Pd = 0.000 to
   Pd = 1.000 inside a ~10 dB window of input SNR (peak SNR ~9 dB to ~26 dB). This was worth
   checking: a sweep over positive input SNR would have produced Pd = 1.000 in every cell.
2. **3 dB of threshold offset is the whole difference between two of the detectors.**
   `cfar_numpy_go` (+12 dB, hard-coded) and `cfar_custom_datasetv8` (+15 dB from the config)
   are the same GO-CFAR on the same dB map. With clutter off, the 12 dB version reaches
   Pd = 1.000 at -30 dB input while the 15 dB version needs -25 dB — about 5 dB of extra
   sensitivity — and pays for it with **~5 false alarms in every single frame**, where the
   15 dB version has exactly zero across all 128 frames.
3. **`cfar_advanced_go` is the most conservative of the three as shipped.** Despite deriving
   its threshold from `pfa=1e-5` in the correct linear-power domain, its `min_snr_db=6.0`
   post-filter plus connected-component pruning make it the last to detect (Pd = 0.000 until
   -25 dB input) — and it degrades worst under `clutter_strong`, reaching only Pd = 0.500 at
   -15 dB where `cfar_custom_datasetv8` reaches 0.938.
4. **The false-alarm rate is independent of SNR, as a CFAR's should be.** `cfar_numpy_go` sits
   at 4.75-5.81 false alarms per frame across a 35 dB span of input SNR. CFAR thresholds are
   relative to a local noise estimate, so they are scale-invariant; the noise realization is
   statistically identical at every SNR point and only the target amplitude moves. Seeing this
   flat is a consistency check on the harness, not a defect.
5. **The accuracy numbers are bin-limited, not noise-limited.** At high SNR the measured range
   RMSE is 0.040 m against a quantization floor of 0.043 m, and velocity RMSE is 0.136 m/s
   against a floor of 0.135 m/s. None of these detectors does sub-bin peak interpolation: they
   report the bin index converted to metres. So the reported accuracy is a property of the FFT
   grid and the reporting convention, and better thresholding cannot improve it — peak
   interpolation (or a model that regresses position) is what would.
6. **`apply_realistic_effects` does essentially nothing at its shipped setting** — see the
   scenario section above for the quantified version.

Statistical caveat: 16 frames per point means Pd is quantized to 1/16 = 0.0625, and a measured
Pd = 1.000 has a two-sided 95% lower confidence bound of about 0.79. Read the transition
region, not the endpoints.

## How to run

Requirements: Python 3.9+, `numpy`, `scipy`, `tqdm`. `matplotlib` is optional (figures only).
**torch is not required and is not installed** — see "Why a shim" below.

```bash
python -m benchmarks.run_benchmark                    # default sweep, writes results/
python -m benchmarks.run_benchmark --update-readme    # also refresh the table above
python -m benchmarks.run_benchmark --quick            # ~15 s smoke run, not a result
python -m benchmarks.run_benchmark --config config1 --trials 8 --no-figures
python -m benchmarks.run_benchmark --help             # every knob
```

Useful flags: `--config` (any FMCW key of `RADAR_CONFIGS`), `--snr-db`, `--trials`, `--seed`,
`--scenarios`, `--gate-range-bins`, `--gate-doppler-bins`, `--pfa`, `--mtd`, `--max-targets`.

Determinism: the repo's simulation calls `np.random.randn` and `random.uniform` on the global
RNGs, which take no injected generator, so the harness seeds both globals per frame from a
`SeedSequence` keyed on `(base_seed, trial)` for the scene and `(base_seed, trial, snr_index)`
for the noise. Consequences, both covered by tests: reruns with the same `--seed` reproduce
byte-identical range-Doppler maps, and **the SNR sweep is paired** — every SNR point sees the
same set of physical scenes, only the noise realization changes.

Tests:

```bash
python -m pytest tests/test_benchmark_metrics.py -q
python -m ruff check benchmarks tests
```

## Why a shim (`benchmarks/repo_shim.py`)

`AIRadarLib/radar_det.py` contains three pure numpy/scipy CFAR detectors and one torch one,
but does `import torch`, `import torch.nn.functional as F` and `import matplotlib.pyplot` at
module scope — so **none** of the numpy detectors can be imported without a multi-gigabyte
torch install. `AIradar_datasetv8.py` is the same: its FMCW signal model is pure numpy, but the
module imports torch, h5py and matplotlib at the top.

Rather than patch the repo (this directory is additive only) or install torch to reach numpy
code, the shim installs minimal placeholder modules for whichever heavy dependencies are
*absent*, imports the repo modules, then removes the placeholders from `sys.modules` again.
Anything genuinely installed is never stubbed. Two guards keep this from becoming a lie:

* `assert_no_stub_dependency` inspects the bytecode of every benchmarked function and fails if
  it references `torch`, `F`, `h5py`, `plt`, `cm` or `cv2`. A test asserts it *does* fire on
  `cfar_2d_pytorch`.
* The shim report (which modules were faked) is recorded in `results/results.json`.

One placeholder detail worth knowing: `torch.Tensor` must exist on the stub, because scipy's
array-API compatibility layer resolves `torch.Tensor` whenever a module named `torch` is
importable, and a bare `ModuleType` makes every scipy call raise `AttributeError`.

`AIRadarDataset` is never instantiated by the benchmark, because its `__init__`
unconditionally generates *and* HDF5-saves an entire dataset. Instead
`benchmarks/scenarios.py` builds a `RadarParams` holder that mirrors the `__init__`
derivation and calls the repo's unbound methods against it. A test constructs one real
`AIRadarDataset` (with `save_dataset` stubbed) for three configs and asserts every derived
attribute and axis matches, so the mirror cannot drift.

## Adding a detector (the plug-in point)

`benchmarks.detectors.Detector` is the extension point. Supply a `run` callable with the
signature `(frame, params) -> list[benchmarks.metrics.Point]`:

```python
from benchmarks.detectors import Detector
from benchmarks.metrics import Point

def run_my_model(frame, params):
    # frame.rd_map_detector_input : float64 [1, 2, num_doppler, num_range]  (real, imag)
    # frame.rd_map_db             : float64 [num_doppler, num_range]        (repo's dB map)
    # frame.rd_map_complex        : complex [num_doppler, num_range]
    peaks = my_model(frame.rd_map_detector_input)          # e.g. a torch RadarNet
    return [
        Point(
            range_bin=r,
            doppler_bin=d,
            range_m=float(params.range_axis[r]),
            velocity_mps=float(params.velocity_axis[d]),
        )
        for d, r in peaks
    ]

Detector(
    name="radarnet_v1",
    source="AIRadar/AIRadarLib/modeling_RadarNet.py",
    description="learned detector, checkpoint xyz",
    run=run_my_model,
    range_gate_low_m=1.0,
)
```

Append it to the list returned by `build_detectors` (or add a registry hook). Nothing in
`metrics.py`, the association rule, the aggregation or the reporting needs to change — a
learned detector is scored by exactly the same rule as the CFAR baselines, which is the point
of building the classical baseline first.

## What this does NOT measure

Be blunt about the scope; this is one slice, not a paper.

* **No learned model is evaluated.** torch is not installed in this environment, so the
  torch-based `cfar_2d_pytorch`, `modeling_RadarNet`, `modeling_TimeNet`,
  `modeling_transformer` and every `AIradar_train*.py` pipeline are untouched. The plug-in
  point above is tested; the model behind it is not.
* **No training, no learning curves, no generalization claim.** Nothing is fitted.
* **Simulation only.** Every number comes from the repo's own FMCW model. No CN0566 / Pluto
  capture, no real-world data, no measured hardware impairments. `config_cn0566` (which enables
  the hardware-impairment model, 2 RX and the array factor) is *not* part of the default sweep.
* **Single RX after coherent summation.** `simulate_fmcw_signal` sums the RX channels before
  the FFT, so the range-Doppler map has one channel. Angle-of-arrival estimation is therefore
  disabled and **no angular accuracy is measured**, even though the detectors can estimate AoA.
* **FMCW only.** The OTFS path (`simulate_otfs_signal`, `config_otfs`) is not covered.
  `RadarParams` refuses non-FMCW configs rather than guessing at their axes.
* **One target per frame by default.** The SNR axis is only unambiguous with a single target,
  because `simulate_fmcw_signal` normalizes noise against the *total* signal power, so with
  several targets of different RCS "the SNR" is not any one target's SNR. Multi-target
  resolution, target masking and merged-detection behaviour are therefore **not** measured.
  `--max-targets N` runs it, but read the Pd column as a scene-average, not a per-target SNR
  curve.
* **The false-alarm numbers are peak-level, not per-cell.** All three detectors apply
  non-maximum suppression (and `cfar_advanced_go` additionally collapses each connected
  component to one peak), so the reported rate is a density of surviving peaks. It cannot be
  compared against a CFAR design `Pfa`, and `--pfa` therefore changes `cfar_advanced_go`'s
  threshold without the output rate tracking it.
* **No detector tuning.** Each detector runs with the parameters the repo ships
  (`RADAR_CONFIGS[...]['cfar_params']`, `min_snr_db=6.0`, `pfa=1e-5`). The comparison is
  "as shipped", not "at its best". A fair ROC would sweep each detector's threshold to a
  common false-alarm rate; this slice does not.
* **Small sample size.** 16 frames per point means a Pd of 1.000 has a 95% lower confidence
  bound near 0.8. Treat the transition region, not the endpoints, as the signal.
* **CPU single-process, one machine.** The timing line is a runtime budget check, not a
  throughput benchmark, and no attempt is made to compare against another implementation.

## Repo issues found while building this

Measured, not inferred. None of these are fixed here (this directory is additive only).

1. `AIRadarLib/radar_det.py` imports `torch` and `matplotlib.pyplot` at module scope, which
   makes its three pure-numpy CFAR detectors unimportable in a numpy-only environment.
   Same for `AIradar_datasetv8.py` (torch, h5py, matplotlib) around a pure-numpy signal model.
2. `AIradar_datasetv8.py` imports `cfar_2d_numpy` from `AIRadarLib.radar_det` and never uses
   it. It cannot be used as written: `cfar_2d_numpy` wants a complex `[num_rx, 2, doppler,
   range]` map, but `simulate_fmcw_signal` only ever returns the dB magnitude map.
3. `cfar_2d_detect` (the first detector in `radar_det.py`) unpacks
   `range_idxs, doppler_idxs = np.where(detections)` on a `[doppler, range]` array — the two
   index arrays are swapped, so its range and velocity outputs are transposed. It is not
   benchmarked here for that reason. `cfar_2d_numpy` and `cfar_2d_advanced` get this right.
4. `cfar_2d_numpy` takes no false-alarm-rate argument; its threshold is a hard-coded
   `noise_est + 12` dB. `cfar_2d_detect` has a `rate_fa=1e-5` parameter that is never read —
   its threshold is also hard-coded at +12 dB.
5. `cfar_2d_numpy` and `_cfar_2d_custom` average the **dB** map to estimate the noise level.
   CA/GO-CFAR is derived for averaging in the linear power domain; averaging in dB estimates a
   geometric rather than arithmetic mean, so the threshold does not correspond to the nominal
   false-alarm rate. `cfar_2d_advanced` does it correctly in linear power.
6. `AIRadarDataset._evaluate_metrics` computes match distance as
   `sqrt(delta_range^2 + delta_velocity^2)` with a threshold of `3.0` — adding metres to
   metres-per-second. It also reports mean *absolute* error under the name
   `mean_range_error`, and there is no Pd, no false-alarm rate and no SNR sweep. This harness
   does not use it.
7. `AIRadarDataset.__init__` unconditionally calls `generate_dataset()` and then
   `save_dataset()`, so merely constructing the object writes an HDF5 file. There is no
   lazy/in-memory mode.
8. `apply_realistic_effects=True` is close to a no-op at the shipped clutter intensity
   (measured -23 dB clutter-to-target RCS power; ~0.03 dB mean perturbation of the RD map),
   because the clutter RCS range (-50..-20 dBsm) sits far below the primary-target RCS range
   (+5..+30 dBsm).
9. `AIradar_model_comparison.py` -- the only script in the repo that sets out to compare
   detectors and produce ROC/PR curves -- imports two modules that do not exist
   (`AIradar_transformer`, `AImodels_joint`). It has never been runnable as committed.
10. `self.range_resolution` is set twice in `__init__`: first as the FFT bin spacing
   `c*fs/(2*slope*zero_pad)` used to build `range_axis`, then overwritten with the Rayleigh
   resolution `c/(2B)`. With `zero_pad_factor=2` these differ by exactly 2x. Any code that
   uses `range_resolution` as a bin spacing is off by that factor.
   `AIRadarDataset.cfar_detection` correctly uses `range_axis[1] - range_axis[0]` instead;
   this harness does the same.
